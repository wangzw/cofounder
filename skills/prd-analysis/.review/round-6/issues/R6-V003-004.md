# aggregate.py TRACE_ID_RE uses permissive `[A-Za-z]` while check-trace-id-format.sh uses canonical `[CPWVRSJ]`

## Finding

The `trace_id` format is canonically defined by **CR-S10 trace-id-format**
(skill-forge/common/review-criteria.md §CR-S10) as
`R<N>-<role-letter>-<nnn>` where `role-letter ∈ {C, P, W, V, R, S, J}`.

Two leaves in my focus subset implement regex-based parsing of `trace_id`:

1. `scripts/check-trace-id-format.sh:38` enforces the canonical 7-letter set:

   ```python
   VALID_PATTERN = re.compile(r'\btrace_id[=:\s]+R\d+-[CPWVRSJ]-\d{3}\b')
   ```

2. `scripts/lib/aggregate.py:241` parses the same field with a *permissive* alphabet:

   ```python
   TRACE_ID_RE = re.compile(r"\btrace_id:\s*(R\d+-[A-Za-z]-\d+)")
   ```

`aggregate.py`'s regex would silently accept (and attribute usage events to) trace IDs
like `R3-Q-007` or `R3-X-007` that the inventory checker would correctly reject. Two
parsers for the same protocol field disagree on what is valid. This violates **CR-L04
(criteria-internally-consistent / cross-reference consistency)**: the metrics aggregator
and the trace-id format checker MUST share a single canonical alphabet, otherwise
divergent `--diagnose` outputs and `run-checkers.sh` outputs across rounds become possible.

A second, smaller divergence: `aggregate.py` uses `\d+` (any number of digits) for the
sequence, while `check-trace-id-format.sh` uses `\d{3}` (exactly 3 digits, matching the
zero-padding convention in the cross-reviewer-subagent.md issue-id contract). The
3-digit rule is the canonical one — `aggregate.py` would also accept `R3-W-7`.

## Why this matters operationally

If a writer sub-agent emits a malformed trace marker (e.g. `R3-W-7` because of a
zero-padding bug in the orchestrator's dispatch loop), `check-trace-id-format.sh` would
file a CR-S10 error against the relevant `.md` / `.yml` file — but `aggregate.py` would
quietly attribute usage events to that malformed trace and report cost numbers that
cannot be cross-referenced with the issue file. The mismatch hides the very malformation
the format check is supposed to surface.

## Suggested fix

Tighten `aggregate.py`'s `TRACE_ID_RE` to match the canonical alphabet and zero-padding:

```python
TRACE_ID_RE = re.compile(r"\btrace_id:\s*(R\d+-[CPWVRSJ]-\d{3})")
```

**Caveat / blocker_scope=cross-artifact-dep**: `scripts/lib/aggregate.py` is sha-pinned via
`common/skeleton/shared-scripts-manifest.yml` (CR-S12 metrics-aggregate-verbatim). Editing
the file in the prd-analysis target without updating the upstream skeleton + the manifest
hash would break CR-S12. The proper fix is at the skill-forge skeleton + manifest;
prd-analysis can then re-scaffold to inherit the corrected file. This issue is therefore a
**warning** in this leaf rather than `error`, and the reviser should escalate via HITL or
cascade rather than patch in place.
