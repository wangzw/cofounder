# common/config.yml: pricing.models keys diverge from model_mapping values — every cost lookup misses, --diagnose pricing column emits 0 silently

## Finding

`common/config.yml` lines 22–45 define two related blocks that MUST share a
key vocabulary. They do not:

```yaml
model_mapping:
  heavy:    claude-opus-4-5     # ← "-5" suffix
  balanced: claude-sonnet-4-5   # ← "-5" suffix
  light:    claude-haiku-4-5    # ← "-5" suffix

pricing:
  models:
    claude-opus-4:              # ← no "-5" suffix
      input_per_1m: 15.0
      ...
    claude-sonnet-4:            # ← no "-5" suffix
      ...
    claude-haiku-4:             # ← no "-5" suffix
      ...
```

`SKILL.md` line 175 documents the contract: the orchestrator writes
`model_requested` (the `model_mapping`-resolved value, e.g. `claude-opus-4-5`)
into `dispatch-log.jsonl`. `scripts/lib/aggregate.py` and
`scripts/metrics-aggregate.sh` then look that ID up against
`config.yml.pricing.models` to compute per-dispatch cost.

**Every lookup fails.** The dispatch log carries `claude-opus-4-5` but the
pricing table is keyed on `claude-opus-4`. The pricing aggregate has no
match-fallback documented anywhere I can see — the cost column for every
dispatch will silently emit `0` (or `null`, depending on the parser's missing-
key handling), and the `--diagnose` cost report will under-count the entire
delivery's spend.

This is a **CR-L04 cross-reference inconsistency**: two `config.yml` blocks
that the runtime joins MUST agree on the join key, and they do not.

## Why this matters (skill-forge–specific anti-pattern)

Skill-forge has a stated cost-control discipline (SKILL.md "Per-dispatch model
override" section, `--no-consultant`, `--tier`, etc.), and `--diagnose` is the
metrics reporter that measures whether cost control is working. If the cost
column always reads `0`, every delivery looks free, and the entire cost
optimization tier (CR-S15 + writer-subagent's "follow the SKILL.md template
exactly" + `model_mapping` discipline) is unobservable in production. The
operator cannot tell if `--no-consultant` actually saved money on a given
delivery.

Cross-reviewer issues R6-V003-004 (aggregate.py TRACE_ID_RE permissive) and
R6-V003-005 (prune-traces.sh wrong key) also surfaced cross-reference drift
between scripts and config.yml, but **neither flagged the pricing-models /
model-mapping divergence** — that's the angle this issue covers.

## Reproduction / verification

```bash
cd /Users/wangzw/workspace/cofounder/skills/prd-analysis
grep -A3 'model_mapping:\|pricing:' common/config.yml
```

Confirms `model_mapping` resolves to `*-4-5` IDs but `pricing.models` keys are
`*-4`. Any aggregator that reads dispatch-log `model: claude-opus-4-5` and
looks up `pricing.models["claude-opus-4-5"]` returns missing.

Spec source: `SKILL.md` line 175 explicitly says the dispatch-log `model`
field is "the config-mapped value for this role's tier (e.g. `balanced` →
`claude-sonnet-4-5`). Used for pricing lookup". So the dispatch log will carry
`-4-5` IDs, and the pricing table cannot match them.

## Suggested fix

Either:

1. **Add `-5` suffix to pricing keys** (preserves model_mapping):
   ```yaml
   pricing:
     models:
       claude-opus-4-5: { ... }
       claude-sonnet-4-5: { ... }
       claude-haiku-4-5: { ... }
   ```

2. **Or change model_mapping to the un-suffixed IDs** (preserves pricing):
   ```yaml
   model_mapping:
     heavy:    claude-opus-4
     balanced: claude-sonnet-4
     light:    claude-haiku-4
   ```

Option 1 is recommended because the `-4-5` IDs are the actual current Claude
model identifiers; pricing should track the real model.

Also: add a script-tier check (e.g. `scripts/check-config-schema.sh`
extension) that asserts every value in `model_mapping.*` exists as a key in
`pricing.models.*`. This is a one-line bash check that would have prevented
this drift; without it, the next config edit can re-introduce the same skew.
