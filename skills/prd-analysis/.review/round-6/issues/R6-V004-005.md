# review/adversarial-reviewer-subagent.md missing trigger-condition gate AND no-op-ACK semantics — adversarial reviewer fires unconditionally on every dispatch

## Finding

`review/adversarial-reviewer-subagent.md` (the prd-analysis copy) is a 78-line
file. The IPC envelope (Snippet D, lines 1–39) is present and correct. The
role-specific body (lines 43–77) is the DOMAIN_FILL stub the cross-reviewer
already flagged in R6-V002-001 / R6-V002-003. **This issue is a different
attack angle from those two.**

The master `adversarial-reviewer-subagent.md` role spec at
`/Users/wangzw/.claude/skills/skill-forge/review/adversarial-reviewer-subagent.md`
defines TWO mandatory contract elements that the prd-analysis copy is missing:

**Element 1 — Trigger Condition Gate (master file lines 102–116):**

> Dispatched by orchestrator ONLY when `config.yml adversarial_review.triggered_by`
> threshold is met (default: any in-generate critical or error issue). Check
> `state.yml` for the `adversarial_review_triggered: true` flag before beginning
> — if absent, emit a no-op ACK and return immediately (do not file false issues).

The prd-analysis copy contains **no instruction** to check
`state.yml.adversarial_review_triggered` before doing work. There is also no
mention of the no-op behavior. The `<!-- TODO: specify trigger conditions -->`
on line 53 acknowledges the gap but does not fill it.

**Element 2 — No-op ACK Form (master file lines 108–112):**

> No-op ACK form (when trigger flag absent in `state.yml`):
> ```
> OK trace_id=<id> role=reviewer linked_issues=
> ```

The prd-analysis copy's ACK Format section (lines 71–77) lists ONE ACK form
— the issue-bearing form `OK trace_id=<...> role=reviewer linked_issues=<list>`
— with no second form for the trigger-not-met case. A sub-agent that follows
this prompt verbatim cannot distinguish "ran and found nothing" from "should
have stayed home". Both will look identical in dispatch-log.jsonl.

## Why this matters (skill-forge–specific anti-pattern — CR-L02 ack-contract-fidelity)

The cross-reviewer's R6-V002-001 (CR-L07 reviewer-prompt-discipline) flagged
the stub body. R6-V002-003 (CR-L04 issue-id key) flagged the schema
mismatch. **Neither flagged that the ACK contract is incomplete** for this
role's specific dispatch semantics.

CR-L02 (ack-contract-fidelity, severity critical) requires every sub-agent
prompt to enforce its full ACK contract. For a conditionally-fired
sub-agent, the contract has two ACK shapes — issue-bearing and no-op — and
the prompt MUST tell the sub-agent which to use when. Without that
instruction:

1. The orchestrator (today) cannot reliably tell from dispatch-log.jsonl
   whether the adversarial-reviewer was a "false fire" (no triggered
   condition) or a "true fire that found nothing" (issues=0 but trigger met).
   These are very different signals for `--diagnose` cost reporting and for
   the convergence-judge logic.
2. A future re-generated prd-analysis where the writer fills the
   DOMAIN_FILL body but follows the existing ACK Format section will produce
   an adversarial-reviewer that ALWAYS files attack-angle issues, even on
   rounds where no critical/error trigger fires — defeating the
   cost-optimization purpose of conditional triggering.

This is the adversarial-reviewer-subagent's signature failure mode against
itself: the prompt that defines how to attack other prompts has its own
ACK contract under-specified.

## Suggested fix

When the writer fills the DOMAIN_FILL body, the body MUST include (taken
verbatim from the master spec, lines 100–117):

```markdown
### Trigger Condition

Dispatched by orchestrator ONLY when `config.yml adversarial_review.triggered_by`
threshold is met. Check `state.yml` for the `adversarial_review_triggered: true`
flag before beginning — if absent, emit a no-op ACK and return immediately
(do not file false issues).

No-op ACK form (when trigger flag absent in `state.yml`):

\```
OK trace_id=<id> role=reviewer linked_issues=
\```

This carries the `reviewer_variant: adversarial` metadata via dispatch-log.jsonl
(orchestrator's responsibility), not the ACK line itself.
```

Additionally, add a defensive read instruction:

```markdown
### Input Contract — Trigger Validation (FIRST STEP)

Before reading any focus leaf, MUST execute:
1. Read `<target>/.review/state.yml` for `adversarial_review_triggered`.
2. If field is `true`, proceed to standard input contract.
3. If field is `false` or absent, emit no-op ACK and return.
```

This makes the adversarial-reviewer self-defensive against misconfigured
orchestrators. It also makes the no-op vs. issue-bearing dispatch
distinguishable in dispatch-log.jsonl: a no-op produces `linked_issues=`
(empty), trigger-met-but-clean produces same shape but the orchestrator-side
launch event will record `adversarial_review_triggered: true`.

Class-scan: I checked the prd-analysis copy of `cross-reviewer-subagent.md`
(non-conditional dispatch — fires every round). It does not need a trigger
gate, so this issue is specific to the adversarial variant. I also checked
the cross-reviewer's "Forced-full override" handling (line 129–130 of
`cross-reviewer-subagent.md`); the conditional behavior there IS specified.
The asymmetry is real: cross-reviewer specifies its conditional flag but
adversarial-reviewer does not.
