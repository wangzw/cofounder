# R6-V001-003: common/domain-glossary.md is empty — DOMAIN_FILL placeholder remains, no terms populated

## Finding

`common/domain-glossary.md` retains the `<!-- DOMAIN_FILL: populated by writer-subagent during round 1 -->`
placeholder (line 3) and the writer-instruction comment
`<!-- Writer: populate this file with terms specific to this skill's artifact domain -->`
(line 13). The body has zero glossary entries — only the table header skeleton.

CR-L02 enforces the ACK contract for sub-agent prompts, and at the system level the
domain-glossary is the file `scripts/glossary-probe.sh` reads (per `from-scratch.md`
Step 3) to compute `glossary_hit` — which the orchestrator routes off to decide
whether to dispatch the domain-consultant. With an empty glossary file:

- `glossary-probe.sh` will produce `glossary_hit: false` for every input, regardless
  of how PRD-domain-laden the user's prompt is.
- The downstream condition for dispatching the domain-consultant in Step 4 of
  `from-scratch.md` is `glossary_hit: true` OR `sparse_input: true`. With an empty
  glossary the consultant only fires on sparse input, never on PRD-vocabulary
  ambiguity (e.g. user says "user story" vs "epic" vs "feature").
- The skill ships a behavior contract that the runtime cannot honor.

This is a global-conflict between the skill's design intent (use glossary terms to
trigger clarification) and the actual artifact (empty glossary). CR-L02 captures
this: the prompt-side ACK / IPC fingerprint exists but the data-side artifact the
prompt depends on is uninitialised.

## Fix

Populate `common/domain-glossary.md` with the prd-analysis vocabulary that should
trigger the consultant. Candidate terms (drawn from the skill's own CLAUDE.md +
`document-mode.md` Parser Heuristics table):

| Term | Definition | Aliases |
|------|-----------|---------|
| `feature` | A bounded user-facing capability with own AC + ID `F-NNN` | epic, capability, story-set |
| `journey` | A persona's end-to-end touchpoint sequence with ID `J-NNN` | flow, user flow, scenario |
| `touchpoint` | One row in a journey's touchpoint table | step, interaction |
| `persona` | A named user archetype with goals + frequency | user type, role |
| `cross-journey pattern` | A theme observed across multiple journeys | shared concern |
| `tombstone` | A deprecated-feature/journey marker file | deprecated stub |
| `interaction mode` | The primary input mechanism at a touchpoint | input type |

A minimum set of 6–10 terms is sufficient to give `glossary-probe.sh` a non-trivial
match surface. Without this fill, the trigger flag `glossary_hit` is dead code.
