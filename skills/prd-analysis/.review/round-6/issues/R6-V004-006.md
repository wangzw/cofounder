# in-generate-review.md CR Applicability table cites CR-S/CR-L (skill-forge meta) but writer-subagent.md self-review uses CR-PP* (prd-analysis) — two incompatible self-review frameworks

## Finding

`generate/in-generate-review.md` lines 11–22 define the CR Applicability table
that the writer sub-agent is supposed to consume during self-review:

```markdown
| File type | Applies CRs | Severity floor |
|-----------|------------|----------------|
| `SKILL.md` | CR-S01, CR-S02, CR-S09, CR-L01 | critical for CR-S01/S02/S09 |
| `*-subagent.md` | CR-S08, CR-L01, CR-L02 | critical for CR-S08 |
| `common/review-criteria.md` | CR-S05, CR-L03 | error |
| `common/config.yml` | CR-S06 | error |
| Any artifact leaf | CR-L02 | error |
```

These are **skill-forge meta-skill criteria** (CR-S01..CR-S09, CR-L01..CR-L03)
that govern *generated SKILL files*, not PRD bundles. They live in
`/Users/wangzw/.claude/skills/skill-forge/common/review-criteria.md`.

But `generate/writer-subagent.md` lines 188–211 define a **completely
different CR Applicability table** for the same writer's self-review:

```markdown
| Leaf type | Applicable CRs |
|-----------|----------------|
| `README.md` | CR-PP01, CR-PP03, CR-PP06, CR-PP07, ... |
| `journeys/J-NNN.md` | CR-PP02, CR-PP16, CR-PP21, ... |
| `features/F-NNN.md` | CR-PP02, CR-PP07, CR-PP12, ... |
... etc, 18 rows total
```

These CR-PP01..CR-PP51 are **prd-analysis's own criteria**, defined in
`<target>/common/review-criteria.md`. They govern PRD artifact leaves.

**The two tables describe completely different things:**

- `in-generate-review.md`: file types are SKILL meta-files (`SKILL.md`,
  `*-subagent.md`, `config.yml`) — i.e., the prd-analysis skill's OWN
  artifacts considered as a meta-skill bundle.
- `writer-subagent.md`: file types are PRD bundle leaves (`journeys/J-NNN.md`,
  `features/F-NNN.md`, `architecture/*.md`) — i.e., the artifacts prd-analysis
  PRODUCES.

Both files are loaded by the writer (per `writer-subagent.md` line 7:
"Self-review discipline is mandatory" and the implicit reference to
`in-generate-review.md` via the in-generate-review topic). The writer cannot
follow both tables — the row keys do not overlap.

This is a **CR-L04 cross-reference inconsistency** at the self-review
contract level. R6-V001-004 mentioned the in-generate-review CR mismatch in
passing as part of the DOMAIN_FILL stub finding. **The angle this issue adds
is the disagreement between the two self-review tables**, which would persist
even after `in-generate-review.md` is filled with prd-analysis CRs — because
the file's framing ("This file is referenced by `generate/writer-subagent.md`")
implies the writer reads BOTH tables.

## Why this matters (skill-forge–specific anti-pattern)

The skill-forge skeleton ships `in-generate-review.md` as a meta-skill self-
review checklist for a writer that produces SKILL files. When skill-forge
generates prd-analysis (a Document-variant skill that produces PRD bundles
of journeys/features/architecture), the writer needs a domain-specific
self-review checklist for the PRD bundle leaves — which is exactly what
`writer-subagent.md` lines 188–211 define inline.

**There should be ONE self-review applicability table per skill, not two.**
The cleanest resolution is one of:

1. Delete `in-generate-review.md` entirely and rely on the inline table in
   `writer-subagent.md`. The two-file structure is leftover skeleton
   scaffolding from skill-forge's own meta-skill self-review pipeline that
   does not apply to prd-analysis's domain.
2. Fold the writer-subagent table INTO `in-generate-review.md` and have
   `writer-subagent.md` reference it by path (single source of truth).

The current file pair has the worst-of-both: a stub meta-skill table the
writer should ignore, plus an inline table the writer should use. The
ambiguity is high-severity because it directly affects the self-review
discipline that all writer dispatches depend on (CR-L09
blocker-scope-taxonomy and the §11.1 self-review FAIL-row escalation chain).
