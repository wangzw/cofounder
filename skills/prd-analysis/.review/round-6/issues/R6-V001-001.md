# R6-V001-001: domain-consultant-subagent.md is essentially unfilled — body contains only TODO placeholders, violating ACK contract specificity

## Finding

`generate/domain-consultant-subagent.md` retains four unresolved TODO comments and a
`<!-- DOMAIN_FILL: populated by writer-subagent during round 1 -->` placeholder where
the role-specific prompt body should live (lines 46–53):

```
# domain-consultant-subagent — Domain Clarification Role for prd-analysis

<!-- DOMAIN_FILL: populated by writer-subagent during round 1 -->

**Role**: domain-Consultant (`C` in trace_id). The ONLY role with `user-interaction: true`.

<!-- TODO: describe the domain clarification questions specific to prd-analysis -->
<!-- TODO: list R-001 through R-007 requirements with domain-specific guidance -->
<!-- TODO: specify the output clarification.yml shape for this skill's domain -->
<!-- TODO: describe dialogue behavior and exit conditions -->
```

CR-L02 requires every sub-agent prompt to enforce the ACK contract — specifically
"Write to final path inside sub-session" + "Task return is one ACK line" — and to
specify what content goes into the final path. Here, the domain-consultant has no
role-specific instructions: the agent has no prompt definition for what dialogue to
run, what `clarification.yml` shape to write, or when to terminate. The IPC envelope
(Snippet D, lines 1–41) is present, but the actual role contract that tells the
sub-agent WHAT to write to `<target>/.review/round-0/clarification/<ts>.yml` is
absent. Without role-specific instructions the sub-agent cannot meaningfully comply
with the ACK contract — it has no anchor for what counts as a complete write.

The `from-scratch.md` Step 4 dispatches this prompt expecting `clarification/<ts>.yml`
with `R-001..R-007` filled and the four flat keys (`SKILL_NAME`, `SKILL_VERSION`,
`SKILL_DESCRIPTION`, `ARTIFACT_ROOT`). With the prompt unfilled, the dispatched
agent will improvise — producing inconsistent output across runs and breaking
planner / writer downstream contracts that depend on the clarification schema.

## Fix

Replace the DOMAIN_FILL placeholder + TODO comments with concrete
prd-analysis-specific instructions:

1. **Purpose**: a one-paragraph statement of the domain-consultant's role for
   prd-analysis (clarify product scope, personas, and PRD intent before the planner
   runs).
2. **Input contract**: list the files the sub-agent reads (`round-0/input.md`,
   `round-0/input-meta.yml`, `round-0/trigger-flags.yml`, `common/domain-glossary.md`).
3. **Dialogue protocol**: describe how to ask one question at a time, terminate on
   `/abort` or "I'm done", and stay within scope (no design / implementation talk).
4. **Output schema** for `clarification.yml`: the exact key set the planner expects
   (`SKILL_NAME`, `SKILL_VERSION`, `SKILL_DESCRIPTION`, `ARTIFACT_ROOT`,
   `R-001`..`R-007` requirement records with domain-specific guidance for each).
5. **DO / DON'T examples** (also satisfies CR-L06 once added): a positive example of
   a well-formed clarification dialogue + a negative example that triggers
   `input-ambiguity` blocker.

Until this body is filled, the skill cannot run a from-scratch generation in
interactive mode without ad-hoc improvisation by the domain-consultant agent.
