# revise/index.md Step 1–2: orchestrator reads issue files and groups them by `file` field — semantic work that violates pure-dispatch (§5.1)

## Finding

`revise/index.md` Step 1 (lines 11–17) and Step 2 (lines 19–32) instruct the
orchestrator to perform semantic analysis on issue files:

```
### Step 1 — Read Open Issue List

The orchestrator reads the issue manifest for the current round:
`<target>/.review/round-<N>/issues/`

- Read frontmatter only (status, severity, file, criterion_id). Do NOT read issue bodies.
- Collect all issues where `status` ∈ {`new`, `persistent`, `regressed`} — these are open.
- Issues with `status: resolved` are already closed; skip them.

### Step 2 — Group Issues by Target File

Group all open issues by their `file` field (the `<target-relative-path>` of the artifact leaf
they point at). Each group becomes one reviser dispatch — one reviser handles all issues
targeting the same leaf.
```

Per `SKILL.md` lines 220–228 (Forbidden Actions, copied here verbatim):

> The orchestrator MUST NOT:
> - Reading artifact leaves
> - **Summarizing content**
> - **Computing convergence verdicts**
> - Rewriting artifacts
> - **Analyzing issue priority**

`revise/index.md` has the orchestrator: (a) reading issue files (a `.review/`
archive, technically permitted), (b) **filtering by status** (analysis), (c)
**grouping by file** (clustering — semantic work), (d) **deciding fan-out
shape** based on the cluster (a planning decision). Step 2's "Each group
becomes one reviser dispatch" is the orchestrator deciding HOW MANY revisers
to dispatch and WHICH ISSUE LISTS to give each one — that is planning, not
dispatch.

In the rest of the skill-forge architecture, **clustering / planning is the
planner sub-agent's job**. The planner has its own prompt
(`generate/planner-subagent.md`) which produces `plan.md`. There is no
analogous planner artifact for the revise loop here — the orchestrator is
acting as planner.

CR-L01 (orchestrator-pure-dispatch, severity critical) requires the
orchestrator to forbid analyzing issue priority. Grouping by file IS
analyzing issue priority — it determines which issues get bundled into a
single revise dispatch versus split across multiple.

## Why this matters (skill-forge–specific anti-pattern)

Per the role/file mapping in every sub-agent prompt's IPC contract section,
the orchestrator's only Write targets are `state.yml` +
`dispatch-log.jsonl`. Its read targets are: ACK lines, `verdict.yml` (judge
output), `plan.md` (planner output for HITL display). It is NOT supposed to:

- Read `issues/*.md` frontmatter
- Compute open-vs-resolved sets
- Group anything

If the revise loop genuinely needs grouping-by-file, that work belongs to a
**revise-planner** sub-agent dispatched before the per-issue-reviser fan-out,
or it should be encoded in a script (`scripts/group-issues.sh` that emits a
plan-shaped YAML the orchestrator just consumes). The current design pushes
LLM-tier semantic work (deciding "this group of 5 issues all target
`writer-subagent.md`, dispatch one reviser") into the orchestrator's
ungoverned context.

This is the adversarial-reviewer's specific attack angle:
**orchestrator-leak by accumulation.** Each individual instruction in Step
1–2 looks small ("read frontmatter only", "do not read bodies"), but the
aggregate is the orchestrator becoming a lightweight planner. The
cross-reviewer's R6-V001-001 / R6-V002-002 caught the per-issue-reviser
prompt being a stub; none caught the orchestration spec that drives the
reviser fan-out being itself an §5.1 violation.

## Suggested fix

Two acceptable resolutions, in order of preference:

**Option A — Introduce a revise-planner sub-agent.** Add a new dispatch step
between current Step 1 and Step 3 that fans out a single planner sub-agent
(reusing `generate/planner-subagent.md` with a `mode: revise` argument, or a
new `revise/revise-planner-subagent.md`). Its output: a `revise-plan.md`
file with the file→issue-list grouping pre-computed. Orchestrator then reads
the plan and fans out per-issue-revisers per Step 3.

**Option B — Move grouping into a deterministic script.** Add
`scripts/group-revise-issues.sh <target>/<round-N>` that reads issues
frontmatter and emits a YAML manifest. Orchestrator reads the manifest (a
script output, not a sub-agent semantic decision) and dispatches one reviser
per group. This is closer to the existing `run-checkers.sh` /
`build-depgraph.sh` discipline.

Either option restores §5.1 pure-dispatch by removing semantic-grouping work
from the orchestrator's hands.
