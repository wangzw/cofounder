## Symptom

`generate/writer-subagent.md`'s "What a well-formed feature leaf looks like" section mandates
a numbered section order (11 sections including "Context", "Requirements", "State Flow", "Edge
Cases", "Implementation Notes") that contradicts the section structure defined in
`common/templates/feature-template.md` (which has "Overview", "Inline Data Model", "Inline
Journey Context", "Inline Conventions", "State Machine", "MVP Boundary Note" as top-level H2
sections with no "Requirements", "Edge Cases", or "Implementation Notes" headings). A writer
dispatched for feature authorship will encounter conflicting blueprints.

## Evidence

**writer-subagent.md** (lines 271–282) mandates this section order for feature leaves:

```
1. Header (# F-NNN: Feature Name + Priority + Effort line)
2. Context (Product, Relevant architecture, Relevant data models, Relevant conventions, Permission)
3. User Stories (As a / I want / so that)
4. Journey Context (inline touchpoint rows from the linked journey)
5. Requirements (numbered, precise, unambiguous)
6. Acceptance Criteria (Given/When/Then, including non-behavioral performance/security criteria)
7. Interaction Design (for user-facing features; omit for backend-only)
8. State Flow (for features with domain object lifecycle; omit for stateless CRUD)
9. Edge Cases
10. Dependencies (depends-on + blocks links)
11. Implementation Notes
```

**feature-template.md** defines these H2 sections (lines 21–130):

```
# F-NNN: {Feature Title}
## Overview
## User Story
## Acceptance Criteria
## State Machine
## Interaction Mode
## Inline Data Model
## Inline Journey Context
## Inline Conventions
## Dependencies
## MVP Boundary Note
## Open Questions
## Change Log
```

**Concrete conflicts** (each is a different section name or ordering disagreement):

| writer-subagent.md says | feature-template.md says |
|------------------------|--------------------------|
| `Context` (with sub-fields) | `Overview` + separate `Inline Data Model`, `Inline Journey Context`, `Inline Conventions` |
| `Requirements` (section 5) | No `Requirements` section |
| `State Flow` (section 8) | `State Machine` |
| `Interaction Design` (section 7) | `Interaction Mode` only |
| `Edge Cases` (section 9) | No `Edge Cases` section |
| `Implementation Notes` (section 11) | No `Implementation Notes` section |
| No `MVP Boundary Note` in list | `MVP Boundary Note` is a required section in template |

The GOOD example in writer-subagent.md (lines 308–343) shows a `## Context` section with
inline data models — which matches the backup template pattern, not the feature-template.md
structure. Writers following the numbered list produce features with different H2 headings than
the template prescribes, causing CR-L07 (terminology-consistency) and CR-L10 (self-containment)
downstream checks to compare against inconsistent baseline expectations.

## Suggested Fix

Reconcile the two sources of truth. One of the following two approaches must be chosen and
applied consistently:

**Option A — Update writer-subagent.md to match feature-template.md** (preferred, since the
template is the canonical scaffold per the plan.add `template:` field):
- Replace the 11-item numbered list with the actual section names from the template.
- Replace the GOOD example `## Context` block with an example using the template's `## Overview`
  + `## Inline Data Model` + `## Inline Journey Context` + `## Inline Conventions` structure.
- Remove "Requirements" and "Edge Cases" from the guidance (they are not in the template).
- Add "MVP Boundary Note" and "Open Questions" to the guidance list.

**Option B — Update feature-template.md to match writer-subagent.md** (requires heavier template
revision):
- Add `## Requirements`, `## Edge Cases`, and `## Implementation Notes` sections to the template.
- Rename `## Overview` to align with "Header + Context" structure from writer guidance.
- Add the "Effort line" to the feature header.
