## Symptom

`review/cross-reviewer-subagent.md` defines an internal set of domain-guidance checks labelled
`CR-S01` through `CR-S10` with PRD-pyramid meanings that directly shadow and collide with the
official `CR-S01`–`CR-S15` criterion IDs defined in `common/review-criteria.md` (which carry
META-skill meanings). Any issue filed by this cross-reviewer against a real PRD pyramid will
use a `criterion_id` field that maps to the WRONG criterion definition in the official registry.

## Evidence

**Official registry** (`common/review-criteria.md`, Criteria Index table lines 12–27):

- `CR-S01` = `skill-md-frontmatter` (checks SKILL.md frontmatter — META-skill structural check)
- `CR-S04` = `criteria-yaml-valid` (checks YAML blocks in review-criteria.md)
- `CR-S05` = `scripts-inventory-match` (checks shell script inventory)

**cross-reviewer internal shadow definitions** (`review/cross-reviewer-subagent.md` lines 193–276):

- `#### CR-S01 — Pyramid Index Consistency` (README must list every J-NNN/F-NNN)
- `#### CR-S04 — Feature-Touchpoint Cross-Reference Integrity` (bi-directional feature/journey refs)
- `#### CR-S05 — Self-Contained Leaf Check` (feature files must be independently readable)

**Concrete collision in the positive example** (`review/cross-reviewer-subagent.md` line 360):

```yaml
criterion_id: CR-S04
```

This example issue is about touchpoint reference integrity (the internal CR-S04 meaning), but
the official `CR-S04` is `criteria-yaml-valid`. When the judge reads this issue's frontmatter
and the reviser consults `common/review-criteria.md` to understand the violated criterion, they
will look up "criteria-yaml-valid" and apply the wrong fix guidance. The tracking system
(dispatch-log, metrics-aggregate) correlates issues by `criterion_id`; these entries produce
phantom metrics for META-skill script checks that never fired.

All 10 internal shadow IDs (`CR-S01`–`CR-S10`) collide with official IDs. The full collision map:

| Internal (cross-reviewer) | Internal meaning | Official meaning |
|--------------------------|-----------------|-----------------|
| CR-S01 | Pyramid Index Consistency | skill-md-frontmatter |
| CR-S02 | ID Format Validity | mode-routing-complete |
| CR-S03 | Frontmatter Completeness | config-schema-valid |
| CR-S04 | Feature-Touchpoint Cross-Reference Integrity | criteria-yaml-valid |
| CR-S05 | Self-Contained Leaf Check | scripts-inventory-match |
| CR-S06 | Design Token Name Consistency | scaffold-sha-pinned |
| CR-S07 | Terminology Consistency | dependencies-loadable |
| CR-S08 | README Cross-Journey Pattern Coverage | ipc-footer-present |
| CR-S09 | Dispatch-Log Snippet Presence | dispatch-log-snippet |
| CR-S10 | Scaffold-SHA Integrity | trace-id-format |

## Suggested Fix

Replace all 10 internal `CR-S0N` section headers in `review/cross-reviewer-subagent.md` with
the correct official criterion IDs from `common/review-criteria.md` that correspond to each
PRD-domain check, OR introduce a new non-colliding namespace (e.g. `CR-PRD-01` through
`CR-PRD-10`) for PRD-pyramid structural checks that are not represented in the current registry.

Specifically, the PRD-pyramid structural checks currently in the cross-reviewer map to existing
LLM-type criteria in the registry as follows (and should reference those IDs instead):

- Internal CR-S01 (index consistency) → official CR-S11 `index-consistency`
- Internal CR-S05 (self-contained leaf) → official CR-L10 `self-containment`
- Internal CR-S07 (terminology) → official CR-L07 `terminology-consistency`
- Internal CR-S08 (cross-journey pattern coverage) → official CR-L11 `cross-journey-pattern-derivation`

The remaining internal checks (ID format, frontmatter completeness, design-token naming,
scaffold-SHA) either map to existing official criteria or should be added to the registry
under new IDs before being referenced in issue files.

Update the positive example at line 360 (`criterion_id: CR-S04`) to use the correct official
criterion ID for the touchpoint-reference-integrity check.
