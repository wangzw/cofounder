# R7-V001-002: SKILL.md mode-routing for `--revise` points at legacy `revise/revise-mode.md`, but `revise/index.md` is the canonical generative-skill orchestration — dual-spec drift in revise mode (same pattern as resolved R6-V004-004 for review)

## Finding

SKILL.md Mode Routing table (line 20):

| revise | `/cofounder:prd-analysis --revise <prd-dir>` | `revise/revise-mode.md`, `common/parallel-dispatch.md`, `common/output-discipline.md` (+ `common/scope-reference.md` + `common/templates/review-checklist.md` on demand) | Per-issue revise loop driven by open issues from last review round; cascade re-review when scope changes |

So the user-facing entry point for `--revise` loads `revise/revise-mode.md`, NOT `revise/index.md`.

But the two files describe **fundamentally different orchestration models**:

**`revise/revise-mode.md` (467 lines, the entry point per SKILL.md)** — interactive 6-step flow with:
- Pre-Answered Mode using a "Clustering Subagent" with `subagent_type: "general-purpose"`, `model: "sonnet"`
- Templates A/B for Fix subagents
- 3-file-cluster cap
- Step 1 (downstream state detection) → Step 2 (PRD overview) → Step 3 (interactive change gathering) → Step 4 (impact analysis) → Step 5 (execute changes via Fix subagents) → Step 6 (delta-focused review)
- REVISIONS.md rolling-detail-window discipline

**`revise/index.md` (111 lines, the canonical generative-skill model)** — pure orchestration with:
- Step 1 invokes `scripts/group-revise-issues.sh` (script-first grouping)
- Step 2 fans out `revise/per-issue-reviser-subagent.md` per leaf group
- Step 3 dispatches `shared/summarizer-subagent.md` for status update
- Step 4 dispatches `shared/judge-subagent.md` for verdict
- The orchestrator MUST NOT read leaf content — pure dispatch + bookkeeping

These are not two views of the same loop — they are two fundamentally distinct revise architectures. A user invoking `--revise` will follow `revise-mode.md` and never reach the generative-skill `revise/index.md` orchestration that calls `per-issue-reviser-subagent.md`. The 222-line per-issue-reviser-subagent.md prompt is therefore unreachable by the user-facing entry point.

This is the exact pattern that round-6's R6-V004-004 surfaced for review-mode (resolved by deleting top-level `review-mode.md` and pointing SKILL.md to `review/index.md`). The same drift now exists for revise mode but was NOT caught in round 6 — and the round-6 cleanup removed `review-mode.md` from the root but kept `revise/revise-mode.md` under `revise/` (CR-S16 only required the mode file to live under a canonical subdirectory, not that it be folded into `index.md`).

## CR-L11 reasoning

CR-L11 explicitly lists this pattern as a violation: "A mode file (e.g. review-mode.md at the skill root) and its canonical counterpart (e.g. review/index.md) ship two different orchestration models for the same `--review` mode, so SKILL.md Mode Routing cannot point to a single source of truth."

The same example, mutatis mutandis, applies here: revise/revise-mode.md and revise/index.md ship two different orchestration models for `--revise`, and SKILL.md points only at one (the legacy interactive one), making the canonical generative-skill counterpart unreachable.

This is NOT a CR-L04 issue — CR-L04 covers conflicts_with pairs only.

## Severity

`critical` rather than `error` because:
1. The unreachable `per-issue-reviser-subagent.md` is a 222-line subagent prompt with extensive prd-analysis-specific revision invariants — substantial wasted work if not reachable.
2. The legacy `revise-mode.md` is interactive (Step 3 asks the user to gather changes), but `--revise` is also the post-review fix-pass driver. The interactive flow is not designed to consume `.review/round-<N>/issues/` machine-output as its primary driver — users invoking `--revise` after `--review` get an awkward UX where the legacy mode tries to detect the issues directory in "Pre-Answered Mode" but does so via Clustering-Subagent rather than the canonical script-first delegation path.
3. The dispatch loop integrity is structurally compromised — `--revise` cannot exit converged via the canonical judge dispatch because that dispatch lives in `revise/index.md` Step 4, which is unreachable.

## Suggested fix

Mirror the round-6 review-mode fix:
1. Fold the substantive content of `revise/revise-mode.md` (interactive change gathering, REVISIONS.md discipline, post-revise cascade) into either `revise/index.md` itself (as a "Pre-Step 0: Interactive Change Gathering" sub-section that runs only when there is no `round-<N>/issues/` directory to consume) OR into a new `revise/interactive-mode.md` that `revise/index.md` Step 0 conditionally loads.
2. Update SKILL.md mode-routing line 20 to point at `revise/index.md` as the canonical entry point.
3. Delete `revise/revise-mode.md` (or reduce it to a stub that points to the canonical index.md).

Alternative (cheaper): explicitly document one as the active orchestrator and the other as historical reference; update SKILL.md's mode-routing accordingly. But this leaves the dispatch loop integrity compromise (point 3 above) unresolved.

This issue should be batched with R7-V001-001 (`scripts/group-revise-issues.sh` missing) — both belong to the revise-mode scaffolding gap. Resolving them together produces a coherent, end-to-end revise pipeline.
