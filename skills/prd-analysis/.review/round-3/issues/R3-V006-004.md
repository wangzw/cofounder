# CR-L02 — `Applicable Design Tokens` section in journey-template is implicitly optional with no condition

## Finding

`journey-template.md` lines 206–221 defines an `Applicable Design Tokens` section for journey files with a note:

> "Copy the relevant design token definitions inline from architecture/design-tokens.md. A reviewer or agent reading only this journey file must not need to open another file to understand which visual/motion properties apply to screens in this journey."

However, the section header in the template does not carry an "Omit if…" condition, and the surrounding Key Rules only say "Copy relevant context inline" without explicitly classifying this section as required vs optional. The journey-template uses this inconsistent pattern: some sections have explicit "Omit for…" conditions while `Applicable Design Tokens` has none, leaving it ambiguous.

In contrast, feature-template explicitly mandates token inlining for all user-facing features. Journey files are read by reviewers and UX agents who need token context for screen validation. Without a clear requirement, writers may omit the section for non-backend journeys that still have visual screens.

## Impact

Journey files without inlined tokens fail the self-contained file principle (CR-L02) for journeys covering UI screens, requiring readers to open `architecture/design-tokens.md` to understand which tokens apply to the journey's screens.

## Fix

Add an explicit condition to the `Applicable Design Tokens` section in journey-template: "Required for journeys covering any UI screens. Omit only for journeys with no user-facing screens (e.g. background job monitoring, CLI-only single-command journeys)." Mirror the explicitness of feature-template's Interaction Design requirement.
