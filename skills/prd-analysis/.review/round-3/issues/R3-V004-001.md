The issue ID format and frontmatter key in the prd-analysis cross-reviewer diverge from the
canonical skill-forge cross-reviewer role spec, breaking cross-reference consistency.

**Offending text (line 159):**
```
Issue ID format: `prd-analysis-round-<N>-<seq>` (zero-padded 3 digits).
```

**Offending frontmatter schema (line 165):**
```yaml
issue_id: prd-analysis-round-<N>-<seq>
```

**Canonical (skill-forge/review/cross-reviewer-subagent.md, lines 174–188):**
```
Issue ID format: R<N>-<seq> where <seq> is zero-padded 3 digits, consistent with
script-emitted issues from run-checkers.sh (§12.5). Start <seq> at max existing in
round-<N>/issues/ + 1, so cross-reviewer IDs never collide with script-tier IDs.
```
```yaml
id: R<N>-<seq>
```

**Why it fails CR-L04 (cross-reference consistency):** The prd-analysis cross-reviewer uses
`prd-analysis-round-<N>-<seq>` as the issue ID scheme and `issue_id:` as the frontmatter key,
while the authoritative cross-reviewer role spec (skill-forge) uses `R<N>-<seq>` and `id:`.
This means issue files written by the prd-analysis cross-reviewer will not be parseable by
scripts and downstream roles (e.g., summarizer, judge) that expect the canonical `id:` key and
`R<N>-<seq>` format. The inconsistency defeats the dispatch-log correlation that
`metrics-aggregate.sh` relies on for round-convergence tracking.

**Example:** the prd-analysis cross-reviewer's own GOOD example at lines 353 and 380 uses
`issue_id: prd-analysis-round-1-007` instead of `id: R1-007`. These two schemas are
incompatible — a script expecting `id:` will not find it.
