The prd-analysis cross-reviewer hardcodes absolute-style skill paths in its Output Contract and
Input Contract, while the canonical skill-forge cross-reviewer role spec uses target-relative
paths. This inconsistency reduces portability and violates the cross-reference consistency
principle.

**Offending text — Output Contract (line 157):**
```
`skills/prd-analysis/.review/round-<N>/issues/<issue-id>.md`
```

**Offending text — Input Contract (lines 118–122):**
```
`skills/prd-analysis/.review/round-<N>/skip-set.yml`
`skills/prd-analysis/.review/round-<N-1>/issues/*.md`
`skills/prd-analysis/common/review-criteria.md`
`skills/prd-analysis/.review/round-<N>/self-reviews/<trace_id>.md`
```

**Canonical (skill-forge/review/cross-reviewer-subagent.md, lines 126–133):** uses
`<target>/.review/round-<N>/...` template paths throughout, where `<target>` is the
skill root injected by the orchestrator at dispatch time.

**Why it fails CR-L04:** Hardcoding `skills/prd-analysis/` instead of `<target>/` makes the
cross-reviewer prompt specific to one path prefix. If the prd-analysis skill is ever moved or
if the orchestrator injects a different target path (e.g., during parallel multi-skill review
runs), the hardcoded paths will fail. The canonical role spec uses `<target>` as a variable
placeholder precisely for this reason. The two versions are inconsistent on this dimension, and
the prd-analysis version is the divergent one.

**Severity rationale:** rated `warning` (not `error`) because the hardcoded path is currently
correct for the prd-analysis skill's actual location, so it causes no runtime failure in the
present deployment. The risk is future breakage on relocation or reuse.
