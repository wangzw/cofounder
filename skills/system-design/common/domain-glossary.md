# Domain Glossary — system-design

This file defines domain-specific terms used by the domain-consultant sub-agent to disambiguate
user intent during the clarification phase, and by all sub-agents (writer, reviewer, reviser) to
ensure consistent vocabulary across the generated design artifacts.

---

## Terms

| Term | Definition | Aliases |
|------|-----------|---------|
| `module` | A bounded unit of system design with a single, named responsibility. Identified by a stable slug of the form `M-NNN-{slug}` (e.g. `M-003-auth`). Lives as a self-contained file at `modules/M-NNN-{slug}.md`. The module file is the unit of writer fan-out: one writer per module in parallel. Every module carries a Status (design lifecycle) and an Impl column (code lifecycle) — these are independent tracking dimensions. Distinct from `service interface` (the implementation noun a module exposes) and `component` (a UI framework widget — different concept, shared vocabulary). | unit |
| `API Surface (module table)` | The per-module table that lists every HTTP/gRPC/CLI endpoint the module owns. Required columns (seven): `Method + Path`, `Auth & Role`, `Success`, `Error Codes`, `Request Example`, `Response Example`, `Constraints`. Enforced by L4 structural lint: any row with a missing or empty column is a mechanical violation. The full contract detail lives in `api/API-NNN-{slug}.md`; the API Surface table carries anchor links to those populated examples. Distinct from `API contract file` (`api/API-NNN-{slug}.md`), which is the standalone full-detail spec file. | API surface, endpoint table, API table |
| `Boundary Enforcement` | The per-module table that makes every dependency-layer rule and convention mechanically verifiable. Required columns (four): `Constraint`, `Tool / Lint / Test`, `File Path`, `CI Job`. Descriptive English in any column ("custom lint", "code review rule") is a mechanical violation caught by L3 lint. Rows that cannot be expressed in concrete tool terms belong in `## Implementation Constraints` as advisory, not in Boundary Enforcement. | enforcement table |
| `Feature-Module mapping matrix` | The README-level matrix that is the bridge between PRD requirements and implementation modules. Rows = PRD `F-NNN` features; columns = design `M-NNN` modules. Cell symbols: `✦` = the module modifies data for this feature (primary ownership), `△` = the module provides read-only support. Every F-NNN feature must have at least one `✦` cell (X5 lint); every module column must list its source features. The matrix is the key input for `/autoforge`. | mapping matrix, feature matrix, F-M matrix |
| `Implementation Conventions table` | The README-level table that translates every PRD `architecture/*.md` topic file into a row: `Category`, `PRD Policy`, `Implementation Pattern`, `Enforcement`. Must be enumeration-complete: every architecture topic file must appear as a row OR be explicitly marked `N/A — {reason}`. Silent omission is a mechanical violation caught by X3 lint. Module-level `Relevant Conventions` sections reference these translated patterns, not raw PRD policy text. | conventions table |
| `Dependency Layering` | The forward-only layer order declared in README's `## Dependency Layering` section. Modules may only import from modules in the same layer or layers to their left. Any edge `A → B` where layer(B) > layer(A) without a documented cross-cutting exemption is a reverse-layer import — a blocker violation (X6 lint). Permitted resolutions: (a) extract a shared interface into a lower layer, (b) relocate the callee, (c) file a documented cross-cutting exemption linked from the Dependency Layering section. | layer order, forward-only deps |
| `Status lifecycle (design-level)` | The four-state lifecycle of a design document: `Draft → Finalized → Implementing → Implemented`. Tracks the design document's readiness, not code progress. Stored in the README's `Design Input` block. See also: Impl tri-state for the independent code-progress dimension. | design status, document status |
| `Impl tri-state (module-level)` | The three-state code-progress tracker in the Module Index `Impl` column: `—` (NotStarted) → `In Progress` (InProgress) → `Done`. Tracks whether code exists for the module, not whether the design is complete. Independent of the design-level Status lifecycle — a module can be `Status=Finalized` and `Impl=—` (fully designed, not yet coded). Updated by autoforge or manually. | impl status, code status |
| `structural-lint` | The mechanical, deterministic, grep-runnable quality gate that runs BEFORE semantic design review in every mode (generate, `--review`, `--revise`). Each check is one bash script under `scripts/check-*.sh`, aggregated by `scripts/run-checkers.sh`. Output lands in `<design-dir>/.review/round-<N>/issues/<issue-id>.md` (issue IDs follow `I-\d{3,}` per `common/issue-schema.md`). Findings are always `blocker` or `mechanical` — no suggestion tier. Mechanical findings NEVER reach the semantic reviewer; if a reviewer re-discovers a lint-covered gap, lint was skipped. Per-file checks: L1–L5. Cross-file checks: X1–X8. | lint, structural lint, mechanical gate |
| `design-review` | The semantic, LLM-driven quality gate that runs AFTER structural-lint passes. Executed by `cross-reviewer-subagent.md` and `adversarial-reviewer-subagent.md`. Applies `common/review-criteria.md` dimensions of type `LLM` only — script-type CRs are filtered because `run-checkers.sh` already covered them. Findings land in `<design-dir>/.review/round-<N>/issues/<issue-id>.md` (issue IDs follow `I-\d{3,}` per `common/issue-schema.md`; the dispatch `trace_id` `R<N>-V-<seq>` / `R<N>-V-<seq>-ADV` is recorded inside the issue, not used as the filename). Dimensions that have lint coverage only require semantic judgment on the dimension's intent, not re-checking structural presence. | semantic review, LLM review |
| `two-phase quality gate` | The paired execution of structural-lint (phase 1) then design-review (phase 2) that governs every mode producing or consuming artifacts. Invariant: phase 2 never runs unless phase 1 exits clean. All findings (lint and semantic) land in `<design-dir>/.review/round-<N>/issues/<issue-id>.md`. Applied in generate (step 9 = lint, step 10 = review), `--review` (step 1.5 = lint, step 2 = review), and `--revise` (step 7.0 = lint gate, step 7 = delta review). | quality gate, lint-then-review |
| `self-contained file` | A module spec, API contract, or README that a coding agent can read independently and start work from. All context a consuming agent needs — data model definitions, interface types, relevant conventions, dependency details — is copied inline into the file, not referenced by path. A coding agent implementing a module reads that ONE module file; it must never need to open a sibling file to understand its contract. Enforced semantically by review-criteria CR L02 and per the Self-Contained File Principle in `CLAUDE.md`. | self-contained, standalone artifact |
| `Module Interaction Protocols` | The README-level table that enumerates every `(caller → callee)` cross-module dependency pair. Columns: `Interaction`, `Caller → Callee`, `Method`, `Data Format`, `Error Strategy`, `Contract Test`. This table and each module's `Deps (direct)` cell are two views of the same data — bidirectional sync is mandatory. X1 lint enforces that every Deps edge has a matching Protocols row and every Protocols row has a matching Deps edge. Orphan rows in either direction are blockers. | interaction protocols, cross-module protocols |
| `Mode` | The execution mode of the skill, selected by CLI flags: `generate` (default, no flag — full multi-round generation from PRD or draft), `--review <design-dir>` (read-only lint + semantic review over existing design), `--revise <design-dir>` (consume open issues from `.review/round-<N>/issues/`, apply fixes, re-run lint gate), `--diagnose` (pure-script metrics aggregation from harness JSONL). Mode routing is declared in `SKILL.md` and dispatches to the relevant sub-agent prompts under `generate/`, `review/`, `revise/`. Distinct from UI-level "mode" (e.g. "edit mode" / "view mode" inside a frontend module's State Management section). When ambiguous, prefer `skill mode` for execution mode and `UI mode` for view-state. | skill mode, execution mode |
| `API contract file` | A self-contained file at `api/API-NNN-{slug}.md` holding the complete specification for one API group. Each endpoint within the file has seven required subsections (enforced by L1 lint): `Description`, `Authentication & Permissions`, `Request` (table), `Request example` (populated JSON), `Response` (table), `Response example` (populated JSON), `Constraints`. No placeholder tokens (`TODO`, `...`, `{}`, `TBD`) permitted in fenced code blocks (L2 lint). Every endpoint in `api/` must be claimed by at least one module's API Surface (X2 lint); orphan endpoints are blockers. Distinct from `API Surface (module table)`, which is the summary table inside a module file linking to this spec. | API file, api/*.md |
| `REVISIONS.md` | The append-only revision history file created on the first `--revise` run. Each entry records: date, source issue IDs (e.g. `I-007, I-014`) from `.review/round-<N>/issues/`, modules touched, and a summary of changes. The README's `References` section links to `REVISIONS.md` once it exists. X8 lint verifies that the README link resolves iff the file exists. | revision history, change log |
| `cross-document path` | A relative file-system path from the design directory to a PRD artifact (e.g. `../../../prd/2026-04-09-foo/features/F-001-slug.md`). All inter-directory references MUST use relative paths so design directories are portable. Absolute paths are forbidden. X8 lint checks that every path in README's References section resolves. | relative path, PRD reference path |
| `service interface` | The TypeScript/Go interface a module exposes at implementation time — the implementation noun (e.g. `interface AuthService { ... }`). Distinct from `module` (the design unit that owns the implementation): a module may expose 0..N service interfaces. The term "service" in implementation templates refers to this concept, not to a design-level module. | service, implementation interface |
| `Interface` | Polysemous in this codebase: (1) a module's `## Public Interfaces` section listing public function/method signatures for the module's own implementation; (2) a row in README's `## Module Interaction Protocols` table describing a cross-module call contract. (1) is owned by the module file; (2) is owned by the README. When the term is ambiguous, use `module interface` for (1) and `interaction protocol` or `protocol row` for (2). | module interface, interaction protocol |
