# generate/feature-delta.md — Feature-Level Delta Analysis

Loaded by the orchestrator when `delta <design-dir> F-NNN` is provided.
Reads the feature-module map to determine which modules are affected by a single
feature change, updates the affected module specs, and outputs the regression-test scope.

This is a **lightweight** operation — no planner, no review loop, no multi-module fan-out.
It dispatches one writer per affected module (modified sequentially or in parallel).

## Contract

- **Input:** design directory + target feature ID
- **Output:**
  1. Affected module list (writes + reads)
  2. Updated module spec(s) for affected modules
  3. Regression-test scope (other features whose own modules overlap with the affected set)
  4. Updated CHANGELOG entry

## Precondition

The design directory must contain `feature-module-map.yml` (generated by system-design
global mode at initial creation). If the file does not exist, exit with error:

> `feature-module-map.yml` not found in {design-dir}. Run `/system-design <prd-dir>`
> first to generate a full design with the feature-module mapping.

## Orchestration Sequence

### Step 1 — Git Precheck

```bash
scripts/git-precheck.sh
```

### Step 2 — Read feature-module map

Read `{design-dir}/feature-module-map.yml`. Locate the entry for F-NNN:

```yaml
F-003:
  name: "Payment Flow"
  writes: [M-001, M-005, M-007]
  reads: [M-006]
```

If F-NNN is not in the map, exit with error:

> F-{NNN} not found in feature-module map. Available features: {list}.

### Step 3 — Compute affected module set

The affected module set = `writes ∪ reads`. For each module in this set, determine
the action:
- **Module in `writes`**: the module spec needs to be updated (API contract, data model,
  state flow changes from the feature change)
- **Module in `reads`**: the module spec may need minor updates (acknowledging the
  feature change) but typically no API/interface changes

### Step 4 — Read the changed PRD feature file

Read the modified PRD feature file for F-NNN (from the PRD directory linked in the
design README's Design Input section). Extract:
- The change summary (what behavior changed)
- Updated acceptance criteria
- Updated API contracts (if any)
- Updated data model entities (if any)
- Updated state flow (if any)

### Step 5 — Dispatch writer(s) for affected module specs

For each module in the `writes` set:

- Dispatch: `generate/writer-subagent.md`
- Role: `writer`
- Inputs:
  - The existing module spec file content
  - The F-NNN feature change summary
  - The relevant PRD feature sections (ACs, API contracts, data models, state flow)
- The writer must:
  1. Read the existing module spec
  2. Update only the sections affected by the F-NNN change (API contracts, data model,
     dependencies, etc.)
  3. Preserve the module's existing frontmatter and ID
  4. Self-audit with `scripts/check-module.sh modules/M-NNN-*.md`
  5. Return the modified module spec

For modules in the `reads` set, the orchestrator skips module spec updates unless
the feature change modifies a data model that the module reads — in that case,
update the module's data model section.

Modules are independent (they are separate files), so dispatch them in parallel.

### Step 6 — Compute regression-test scope

Scan the entire `feature-module-map.yml`. Find all features (other than F-NNN)
whose `writes` or `reads` overlap with the affected module set from Step 3:

```yaml
# Example: F-003 affects M-001, M-005, M-007
# F-007 writes [M-005, M-008] → overlaps M-005 → F-007 needs regression testing
# F-001 reads [M-001] → overlaps M-001 → F-001 needs regression testing
```

Output the regression-test scope as a list of feature IDs.

### Step 7 — Update CHANGELOG

Append to the design's `CHANGELOG.md`:

```markdown
## {YYYY-MM-DD}

### delta F-{NNN}: {Feature Name}
- **Trigger:** PRD F-{NNN} modified
- **Affected modules:** M-{ids}
- **Regression scope:** F-{ids} (features sharing affected modules)
```

### Step 8 — Report

Output a structured summary:

```
Delta analysis for F-{NNN} ({Feature Name})

Affected modules:
  Writes: M-{ids}
  Reads:  M-{ids}

Module specs updated:
  {list of module spec files with changes}

Regression-test scope:
  F-{ids} — these features share affected modules

Next: /autoforge feature F-{NNN}  (to implement changes in affected modules)
```

## FORBIDDEN

- Dispatching a planner
- Entering the review loop
- Modifying module specs for modules NOT in the affected set
- Modifying the feature-module map (the map is only regenerated by global mode)
