# CR-L11

review/index.md pins reviewers to `model: sonnet` while SKILL.md tier table maps reviewer→heavy→opus

## Reasoning

`SKILL.md` "Per-dispatch model override (MANDATORY for cost control)" table:
> "| reviewer (cross + adversarial) | `heavy` | `\"opus\"` |"

`review/index.md` Step 4a (Cross-Reviewer dispatch):
> "Sub-agent type: `general-purpose`; model: `sonnet` (tier alias — do not pin a version)"

Step 4b (Adversarial-Reviewer dispatch) repeats the same `sonnet` instruction. And the file's "Hard Rules" section reinforces:
> "All revisers run on `model: sonnet` (balanced tier)."

But the reviser tier from SKILL.md is `balanced → sonnet`, which is correct; the contradiction is specifically for the reviewer rows, not reviser. SKILL.md says reviewer = `heavy` (opus); review/index.md says reviewer = `sonnet`. This is a direct CR-L11 conflict — two files declare different model-tier assignments for the same role.

The cost implication is large: opus is roughly 5× sonnet for the reviewer dispatch. The CR-S15 cost-control sections gate exists specifically to prevent this kind of silent tier drift; here the drift is encoded into the orchestration file rather than missing-section.

The bigger semantic risk is that the orchestrator (which loads `review/index.md` for `--review` mode) will follow the local instruction and dispatch sonnet, while inside the from-scratch.md generate-mode loop it will follow SKILL.md and dispatch opus. Same role, two model tiers depending on entry point — and `--diagnose` will flag the inconsistency as observed-vs-requested model drift.

## Suggested Fix

Change `review/index.md` Step 4a and 4b to read "model: opus (heavy tier alias)" — matching SKILL.md. Keep the reviser tier (`sonnet`) since that one already matches SKILL.md. Alternatively, if the team has decided reviewers should be sonnet for cost reasons, update SKILL.md to match — but in either case, only one source of truth.
