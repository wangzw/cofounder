# Cross-reviewer prompt directs sub-agent to read PRD content but skip-set never enumerates PRD paths

## Attack angle

Path / cross-document brittleness — the prompt assumes paths the orchestrator cannot guarantee. PRD-coupling failure described in attack vector 8.

## Evidence

The cross-reviewer is told to perform several semantic checks that REQUIRE reading PRD files:

- `cross-reviewer-subagent.md` line 252: "MUST verify (using README's Feature-Module mapping matrix) that every PRD feature has at least one module marked `✦`." — needs PRD feature inventory to detect orphans.
- Lines 258-262 CR-D05: NFR coverage — needs every PRD NFR to compare. PRD NFRs live in `<prd-dir>/architecture/*.md` and `<prd-dir>/features/F-*.md`.
- Lines 271-275 CR-D07: "every risk marked high-likelihood or high-impact in the PRD has a corresponding mitigation." — needs PRD risk inventory.

Yet the input contract (lines 142-152) lists ONLY:
- `<target>/.review/round-<N>/skip-set.yml`
- Each leaf in `cross_reviewer_focus` (i.e. design files only)
- Previous-round issues
- `common/review-criteria.md`
- Self-reviews

`skip-set.yml` is generated by `run-checkers.sh` and contains design-dir-relative paths only (verified by reading `.review/round-1/skip-set.yml` here — every entry is under `common/`, `generate/`, `review/`, etc.; no PRD paths). The cross-reviewer has no way to know where the PRD lives.

The orchestrator could inject the PRD path via `state.yml` — but `state.yml` (read at top of file) carries `target`, `delivery_id`, `current_round`, `mode`, `clarification_path`, `input_path`, `created_at`, `reviewer_version_seen`. No `prd_path` field. The clarification yml DOES carry it (`R-001` in domain-consultant output) but the cross-reviewer is not told to read clarification.yml.

## Concrete failure

Round 1 cross-reviewer reads design leaves only. It cannot see PRD features, so:
- CR-D01 (orphan PRD feature detection) silently passes — no PRD inventory means no orphans found.
- CR-D02 (data-model contradictions across files) is restricted to design-internal contradictions; PRD-vs-design contradictions are silently missed.
- CR-D05 (every PRD NFR has module decomposition) silently passes if reviewer can only see design.
- CR-D07 (every high-impact PRD risk has mitigation) silently passes if reviewer cannot read risks.

Effect: in pure read-only mode, the reviewer reports green on a design that ignored half the PRD. CR-X3 (architecture coverage) and CR-X5 (feature-module traceability) are script-tier and would catch the structural side, but the SEMANTIC side (whether the F-NNN module actually delivers the feature, not just claims `✦`) is owned by CR-D01/D10 and requires PRD reading.

## Fix

Add to the cross-reviewer input contract (and the `--review` index.md Step 4a sub-agent inputs):

| Source | Purpose |
|--------|---------|
| `<target>/.review/round-0/clarification/<latest>.yml` | `R-001` field gives PRD root path |
| OR `<target>/README.md` Design Input section (the writer fills `Source: [PRD_NAME](PRD_PATH)`) | extract PRD path from the link |
| `<prd-dir>/README.md`, `<prd-dir>/features/F-*.md`, `<prd-dir>/architecture/*.md` | read for orphan/NFR/risk semantic checks |

Add an explicit section "PRD-relative checks" enumerating which CR-D dimensions REQUIRE PRD content and listing concrete grep patterns the reviewer should use against PRD content (e.g. "every `## Risks` H2 in PRD features → check the corresponding module's Error Handling for a row referencing the risk by name").

Also: extend `state.yml` schema with `prd_path: <absolute path>` written by the orchestrator after Step 2 (prepare-input). That makes PRD-coupling explicit and reviewable.
